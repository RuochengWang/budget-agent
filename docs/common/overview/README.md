# 项目总体结构（A—E 全员先读）

本文件说明我们共同开发什么、各部分放在哪里、每个人负责哪一段。
接着阅读 [系统流程图](flowcharts.md)，具体文件用途可查 [文件地图](file_map.md)。

## 我们要完成什么

用户输入想买的商品、预算和个人需求。系统计算生活费约束，查询有限优惠，
通过欲望、理性、优惠、裁判四个角色分析，最后给出购买、等待、放弃或补充信息的建议。
最终建议应带有预算结果、付款明细、证据和可回放记录。

五个人是开发分工，系统运行时有四个角色。它们可以使用同一个学校文本模型，
通过各自提示词与上下文承担不同职责；预算和优惠金额由程序计算。

当前仓库是协作骨架：公共协议、流程、记录和最小界面已有基础实现。
离线模式使用演示替身；正式预算、通用优惠求解、角色策略和评测尚待成员完成。
完整现状见根目录 [README](../../../README.md)。

## 五人如何衔接

| 成员 | 主要交付 | 与其他模块的连接 |
|---|---|---|
| A | 数据协议、调度、模型连接、异常与记录、集成 | 把 B/C/D 的模块接入同一条流程，提供给 E 调用 |
| B | 预算工具与理性角色 | 为 D 提供可信的预算结果，协助 C 人工复核优惠 |
| C | 商品/优惠查询与有限优惠求解 | 为 D 的优惠角色提供可调用工具 |
| D | 欲望/优惠/裁判、交叉回应与程序检查 | 使用 B/C 结果，形成有依据且符合约束的建议 |
| E | 界面、案例、评测、报告与演示 | 通过 A 的统一入口运行系统，组织全员验证 |

所有入口共用 `workflow.run_case()`。模块间传递的数据对象在 `schemas.py` 中定义，
具体含义在 [contracts.md](../contracts.md) 中约定。
每个人先了解上下游，再实现个人模块；公共字段或签名变化需要同步调用方。
